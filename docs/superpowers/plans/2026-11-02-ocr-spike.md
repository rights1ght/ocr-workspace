# OCR Spike (Этап 0 ТЗ) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Доказать на фактах, что Surya 2.5 на целевом ПК (Ryzen 16 потоков, 14 ГБ RAM, без GPU) даёт приемлемое качество русского OCR и приемлемую скорость, и получить зафиксированные версии + параметры для этапов 1–4.

**Architecture:** Изолированный каталог `OCR/spike/` с выкидным кодом: установка окружения (uv + Python 3.12), llama.cpp CPU, веса GGUF Q8_0, прогон фикстур на трёх DPI, авто-замеры (время, RSS, доля блоков ниже 0.8), CER на эталонных страницах, прототип HTML→Markdown. Результат — `OCR/spike-report.md` с таблицей порогов из приложения D ТЗ.

**Tech Stack:** uv, Python 3.12, surya-ocr, llama.cpp (`llama-server`), Pillow, pypdfium2, pdfplumber, markdownify, stdlib `resource`/`subprocess`.

**Spec:** `OCR/TZ.md` (раздел 12, этап 0; приложения A/D; раздел 8.1).

## Global Constraints

- Python строго 3.12 окружение через `uv` (ТЗ NFR-3: 3.14 не совместим с torch). Установка: `uv venv --python 3.12`.
- PyTorch только CPU-сборка: `uv pip install torch --index-url https://download.pytorch.org/whl/cpu` (система без NVIDIA, CUDA-сборка ~2.5 ГБ не нужна).
- Без Docker (NFR: на машине Docker не установлен) — только бинарник llama.cpp.
- Программа слушает только loopback; spike не запускает никаких серверов кроме `llama-server` на `127.0.0.1:8181`.
- Оригиналы документов не изменяются (ТЗ 1.4); spike только читает.
- Spike-код — выкидной: тесты не пишутся, коммиты — раз в конце, каталог `OCR/spike/` не попадает в прод-структуру (ТЗ 12, этап 0).
- Целевые пороги — из ТЗ приложение D; каждое измерение сравнивается с ними.

## Review Focus

(Провал этих пяти сценариев означает, что spike даёт ложное «всё хорошо».)

1. **Страница без текста с мелким шрифтом при 96 DPI.** Ожидается: растворение мелкого текста в артефакты; обязана фиксироваться CER-замером на 96 DPI отдельно, а не только на 150. Тест — в Задаче 4 (строка замера CER per-DPI).
2. **`llama-server` без `--special`.** Ожидается: разбор блоков Surya падает или пустой HTML; обязана быть проверка, что запуск БЕЗ флага даёт ошибку/мусор, чтобы прод-код знал про флаг. Тест — в Задаче 3 (негативный прогон).
3. **Таблица с объединёнными ячейками.** Ожидается: сырой HTML содержит `data-cs`/`data-rs`/ghost-спаны; обязана быть проверка, что `clean_block_html` превращает их в валидную таблицу. Тест — в Задаче 5.
4. **Фото без EXIF-поворота (повёрнуто на 90°).** Ожидается: мусорное распознавание; обязана быть проверка, что EXIF-ориентация реально применяется и фиксируется. Тест — в Задаче 5 (сравнение повернутого и оригинального файла).
5. **Перегрев/троттлинг на длинной очереди.** Ожидается: время страницы К-20 заметно выше времени страницы 1; обязана быть линейка «время vs номер страницы» в отчёте, а не только среднее. Тест — в Задаче 4 (график/таблица per-page).

### Task 2: llama.cpp и веса GGUF

**Files:**
- Create: `OCR/spike/models/` (веса, вне git)
- Create: `OCR/spike/get-llama.sh`

**Interfaces:**
- Consumes: окружение Задачи 1 (для скачивания с HF через `huggingface_hub`, уже стоит как зависимость surya).
- Produces: исполняемый `llama-server` в `OCR/spike/bin/`; веса GGUF в `OCR/spike/models/`; скрипт запуска `OCR/spike/run-server.sh`, используемый и в проде (этап 1 оркестрация будет брать параметры отсюда).

- [ ] **Step 1: Скачать бинарник llama.cpp**

Взять последний релиз с ассетом `*-bin-ubuntu-x64.zip` → `OCR/spike/bin/`. Проверка: `./bin/llama-server --version` печатает `ggml` + номер билда. Информацию по совместимым ассетам взять с последнего релиза `ggml-org/llama.cpp` (модель до updatedAt, после — webfetch, страница релизов).

- [ ] **Step 2: Скачать GGUF Surya 2.5**

Через `huggingface_hub`: `snapshot_download("datalab-to/surya-ocr-2.5", local_dir=...)` с фильтром `*.gguf`. Проверка: `.gguf` и `-mmproj.gguf` на месте (vision-проектор обязателен). Размер сверить с ожидаемым ~0.9 ГБ Q8_0; если Q8_0 нет на HF, собрать через `python -m surya.scripts.build_gguf --outtype q8_0` (в отчёте — зафиксировать путь/размер/хеш).

- [ ] **Step 3: Запустить сервер и проверить ответ**

```bash
./run-server.sh   # llama-server -m <gguf> --mmproj <mmproj> --port 8181 --special --parallel 2 --ctx-size 24576
```
Проверка: `curl -s 127.0.0.1:8181/health` → `{"status":"ok"}`. Зафиксировать RSS сервера (`ps -o rss= -p $(pgrep -f llama-server)`) ≤ 3 ГБ; иначе признать Q8_0 неподъёмным и пересадить на Q4_K_M (шаг 2 повторить).

- [ ] **Step 4: Негативный прогон без `--special` (Review Focus #2)**

Перезапустить сервер без `--special`, вызвать `surya_ocr` на `synth/12pt.png`. Ожидаемо видео пустой/битый `results.json` или исключение парсера. Взаимный вывод в отчёт: флаг `--special` обязателен, `results.json` с прошлого шага сохраняется как свидетельство `special-missing-result.json`.

- [ ] **Step 5: Перезапустить сервер с `--special` и оставить работать**

```bash
./run-server.sh &
sleep 5 && curl -s 127.0.0.1:8181/health
```
Проверка: `{"status":"ok"}` — сервер до конца Задачи 5 не гасится.

### Task 4: Основной прогон Surya (замеры времени/RAM/уверенности)

**Files:**
- Create: `OCR/spike/measure.py`
- Create: `OCR/spike/measure-results/{dpi,doroga}/per-page.csv`
- Create: `OCR/spike/measure-results/summary.md`

**Interfaces:**
- Consumes: `OCR/spike/run-server.sh` (Задача 2), `fixtures/` (Задача 3), Python API `RecognitionPredictor` (v2-style API, ТЗ 8.1).
- Produces: `per-page.csv` со столбцами `file,page,dpi,seconds,rss_kb,n_blocks,low_conf_ratio`; `summary.md` — агрегат per-DPI.

- [ ] **Step 1: Написать `measure.py`**

Скрипт: берёт список файлов фикстур, рендер PDF в PNG на указанном DPI (`pypdfium2`), читает PNG, в цикле вызывает `recognition_predictor([img])`, записывает `seconds = time.perf_counter()`, RSS процесса через `resource.getrusage(RUSAGE_SELF).ru_maxrss` (и отдельно `ru_maxrss` llama-server), `confidence` по блокам, счётчики строк CSV. RSS-замер ОС-агностичный: `/usr/bin/time -v` не нужен, `resource` достаточно. На каждую страницу — отдельная строка (не агрегат — Review Focus #5).

- [ ] **Step 2: Прогнать 96 / 150 / 192 / 300 DPI по всем фикстурам**

Между DPI перезапуск llama-server (свежий RSS). Каждая страница отдельной строкой.

- [ ] **Step 3: Свести `summary.md`**

Таблица по каждому DPI: среднее/медиана/p95 сек-на-страницу, пик RSS, % блоков `<0.8`. Сравнение с порогами ТЗ приложение D: 96 ≤ 25 с, 150 ≤ 40 с, RAM ≤ 8 ГБ, доля блоков `<0.8` ≤ 15 %. Каждая строка — вердикт ОК/НЕ-ОК.

- [ ] **Step 4: Отдельная линейка «номер страницы vs время» на 20-страничном PDF (Review Focus #5)**

Показать в отчёте гистограмму. Если p90 «последних» страниц > 1.3× первой — отметить троттлинг и ограничить очередь.

### Task 5: Качество — CER и таблицы

**Files:**
- Create: `OCR/spike/cer.py`
- Create: `OCR/spike/measure-results/cer.csv`
- Create: `OCR/spike/measure-results/tables.md`

**Interfaces:**
- Consumes: `fixtures/synth/{truth.txt}` + серый PNG-вывод Задачи 4 (`measure-results`); `fixtures/synth/tables/structure.txt` + распознанный HTML.
- Produces: `cer.csv` (`file,dpi,cer`), `tables.md` (по таблице: столбцов/строк/merged/верно|неверно|частично).

- [ ] **Step 1: Написать `cer.py`**

CER = расстояние Левенштейна между распознанным текстом и `truth.txt`, нормированное на длину эталона. Сборка «распознанного текста» из `blocks[].html` (сравниваем текст из HTML, теги срезаются). Нормализация: убрать лишние пробелы, переводы строк, ѓ→ё.

- [ ] **Step 2: Вычислить CER для synth-фикстур на 96/150/192 DPI**

Порог ТЗ приложение D: CER(150) ≤ 3 %; > 8 % → пересматриваем движок — пробуем Surya 2 (чек-лист — ТЗ приложение D, строка 1).

- [ ] **Step 3: Проверить фото с EXIF-поворотом (Review Focus #4)**

`exif-rotate.py` ставит метку `EXIF Orientation = 6` (+90°) на копию фикстуры; при чтении через Pillow с `ImageOps.exif_transpose` строка текста должна восстановиться в прямое положение, и CER по ней совпасть с CER необёрнутой фикстуры ±0.5 %. Если Pillow не применяет ротацию — факт в отчёт, становится требованием этапа 2 (ручное вращение страницы).

- [ ] **Step 4: Прогнать таблицы и вручную сверить с `structure.txt`**

Прогон: `surya_table` → HTML → `clean_block_html`. Отчёт: колонок/строк/merged распознаны? Содержимое ячеек ±1 слово? Объединения (`colspan`/`rowspan`) на месте? Порог ТЗ приложение D: ≥ 80 % таблиц структурно корректны; < 60 % → предупреждение в отчёте (ручная правка таблиц в MVP, отдельная задача на парсер).
